| `output/提取结果.xlsx` | 字段级明细 40 行 + 汇总 |

### 核心架构升级：字段级兜底
不是"整封邮件拿不准就全交给 LLM"，而是**哪个字段不行补哪个**：
- 规则层高置信字段直接采纳（零成本）
- 缺失/低置信字段单独转 LLM
- 实测：40 个字段中仅 16 个触发兜底（40%），6 次 LLM 调用覆盖 8 封邮件

### 关键数据（真实 DeepSeek API）
| 指标 | 数值 |
|---|---|
| 规则层字段准确率 | 31/40 = **77.5%** |
| 兜底后字段准确率 | 38/40 = **95.0%** |
| 净提升 | **+7 个字段** |
| 触发兜底字段 | 16/40 = 40% |
| LLM 调用 | 6 次（邮件级）|

### 修复的 6 个实现缺陷（规则层 65% → 77.5%）
1. 客户提取吞人名/职位 → 改为**签名行整行匹配**（公司名通常独占一行）
2. 数量重复（主题 `3000pcs` + 正文 `3,000 pcs`）→ 归一化去重
3. `RE_DATE_RELATIVE` 的 MONTHS 未加分组 → `(?:\s+\d{4})?` 只作用于最后一个分支，导致 `end of October` 漏年份
4. 货币符号 ¥/￥ 编码不一致 → 改用 Unicode 码点 `[\u00a5\uffe5$\u20ac\u00a3]`
5. 单位缺 `pc` → `USD 12.50/pc` 丢单位
6. 产品关键词子串重复（`floor tile` ⊂ `ceramic floor tile`）→ 子串去重

### 设计决策：分字段阈值
```python
FIELD_THRESHOLDS = {
    "customer": 0.7,
    "product": 0.85,   # 关键词只能给类别，抽不到型号规格 → 阈值更高，更容易转 LLM
    "quantity": 0.7, "price": 0.7, "deadline": 0.7,
}
```
产品字段 0.8 分属"部分正确"（知道类别，不知型号），若按 0.7 放过等于接受不完整答案。

### 判定口径：严格化（防"多候选蒙对"）
规则层常返回多候选（`1,200 pcs / 800 pcs`），若按"包含即命中"会虚高。
改成**数字序列必须完全一致**才算命中——含糊其辞不给分。

### ⚠️ 剩余 2 个"错"的性质（面试必须能讲清楚）
不是抽错，是**抽得比标准答案更详细**：
- E03 数量：LLM 给「500支（每支6米）」，标准答案只要「500支」
- E05 产品：LLM 给「Ceramic floor tile **600x600mm** / ...」，标准答案没带规格

严格数字序列比较会判错，但真实业务中这些额外信息有价值。
**严格口径报 95%，不做"为了让数字好看而放宽标准"的事。**

### LLM 价值最硬的证据：E06 引用历史仲裁
规则层抽到「1,200 pcs / 800 pcs」「USD 15.20 / USD 16.00」（含糊，无法确定哪个生效），
LLM 正确识别"正文明确要求忽略引用的旧数据" → 输出 1,200 pcs / USD 15.20/pc。
**这是纯正则永远做不到的事**，是本项目含金量最高的一个点。

### ⚠️ 极其重要的诚实边界（面试必须自己先说出来）
**e2e 上的分类 100% 是"错误分析 → 针对性补关键词"达到的，属测试集内优化。**

在**未参与调参的独立歧义集**（ambiguous，6 封）上做泛化验证：
| | 补词前 | 补词后 |
|---|---|---|
| 规则层 | 33.3% | **33.3%（完全没变）** |
| 兜底后 | 83.3% | 83.3% |

结论：
- 补词**没有损害泛化**（无过拟合负面证据）
- 但也**没有真正提升泛化**——它只是修好了 e2e 里那一个样本
- **真实泛化水平看 83.3% 这一档，不是 100%**
- 真实业务预期：规则层直接处理 70-80%，综合准确率 **88-93%**

面试表述：
> "在参与调优的测试集上分类 100%、提取 98%；
> 但在一份从未参与调参的独立歧义样本上，规则层只有 33%，加 LLM 兜底后 83%。
> 后者才是真实水平。我不会拿调优集上的数字当承诺。"

### 整合带来的 1+1>2：分类驱动提取
同一个字段名在不同类型邮件里含义不同：
- 客诉邮件的"数量"= **缺陷数量**（不是订单总量）
- 物流通知的"截止日"= **到港日 ETA**（不是已发生的开船日 ETD）

不给这个上下文，LLM 会"贪多"把相关数字全列出来（E09 返回 `2,400 / 180 pcs`、
E10 返回 `2026-08-28 / 2026-09-25`），看似全面实则无用。
而"邮件是什么类型"这件事，只有先跑完分类才知道 —— **单独做提取模块时拿不到这个信息**。

修复后：E09 数量 → 180 pcs ✓；E10 截止日 → 2026-09-25 ✓
（连带消除了 E10 的优先级误判：原先取到已过期的 ETD，误标"高优先级"）

### 决策层为什么用规则而不用 LLM
企业场景要"为什么把这封标成高优先级"的审计依据。规则决策可解释、零成本、毫秒级，
且该逻辑本身不复杂；LLM 的语义能力应留给分类和提取这两个真正的难点。

### 争议度检测（新增能力，补阈值盲区）
阈值兜底只救"不自信的错"，救不了"自信但错"。
E06 案例：规则层判询盘 80%（≥阈值不触发兜底）但正确答案是订单，
且争议度仅 0.25（询盘4 : 订单1），检测同样无效。
根因是关键词库缺口：只有 PO 号 / 形式发票等"已成单"信号，
缺"接受报价 / 要求投产"这一阶段（如 `we accept the price`、`proceed with production`）。
补充后得分接近 → 争议度检测捕获 → 转 LLM 纠正为订单 ✓

### 遗留：A01 仍未解决（独立集）
"Re: quotation... we'd like to proceed 3000sqm at better price" —— 客户表达下单意向但仍要更优价格，
规则层与 LLM 都判"询盘"，标注为"订单"。属真实语义模糊地带，
说明**人工复核层不是可选项，而是必需品**。

根因：Python 脚本无法调用 WorkBuddy 的 MCP 工具，故"拉邮件"这一步只能由 AI 完成。

### 当前正确的使用方式
麦当在 WorkBuddy 里说一句「处理我的新邮件」→ AI 用 Agent Mail MCP 拉邮件
→ 落成 `data/inbox_snapshot.json` → 跑 `mail_connector.py` → 出 Excel。
除"说一句话"外全自动，耗时 10-30 秒。

### 升级为全自动的方案（待麦当确认后实施）
用 `automation_update` 建定时任务（如每天 9:00）：到点后 AI 自动执行上述全流程。
这是可行路径 —— WorkBuddy 的 automation 是"到点执行一段 prompt"，
即由 AI 在会话内完成 MCP 拉取 + 脚本处理。

### 可移植性结论
| 部分 | 换电脑 | 条件 |
|---|---|---|
| 处理引擎（除 make_snapshot） | ✅ 可 | Python 3.11+ / requests + openpyxl / 填 API Key |
| 邮件拉取（Agent Mail） | ⚠️ 依赖 WorkBuddy | 换机需重新开通（新邮箱地址），或用 JSON 快照替代 |
| 全自动定时 | ❌ 未实现 | 需 automation 定时任务或常驻服务 |

关键：`mail_connector.py` 输入是**标准 JSON**，不依赖 WorkBuddy ——
任何电脑（含 Linux 服务器）只要有邮件 JSON 就能跑。

### 两个新发现
1. **GetMessage 会自动把邮件标记为已读** → "只拉未读"策略天然防重复处理，
   无需额外记录已处理 ID（实测：之前读过的 3 封已变为已读）
2. **非业务邮件会白白消耗 LLM 调用**（每封约 2 次却无产出）
   → 真实收件箱必然混入系统通知/广告/验证邮件
   → **待优化**：加一层便宜的"是否业务邮件"前置过滤（规则层判断，
   不含任何外贸关键词 + 不含数量/价格单位 则直接跳过，不调 LLM）

### 清洗函数的一个已知局限
无法去重响应式邮件的 web/app 双版本 HTML（两套内容都在 body 里，清洗后正文重复）。
本次欢迎邮件即如此。对外贸业务邮件的字段提取影响不大，但值得记录。
