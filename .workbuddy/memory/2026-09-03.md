### 关键设计决定

1. **双路引用归一**：答案内联 `[n]`（给人看）+ JSON `cited` 数组（给机器验），取并集。
   任一路缺失不算失败但都记录
2. **不掩盖问题（对计划的偏离）**：答案零引用时**不回退模板**（模板同样没引用，回退只是掩盖），
   改打 `no_citation` 标记交评测层计失败。仅异常 / 超时 / JSON 解析失败才回退
3. **复用不重写**：直接调 `DeepSeekProvider.raw_call()`，沿用其 temperature=0 + JSON 模式；
   配置读取复用 `FallbackManager._load_config()`；日志复用 `output/llm_calls.jsonl`
4. `parse_llm_json` 是分类专用（硬编码 category 字段），所以生成端自己写了 `_parse_json_content`

### 实测结果

- 真实生成 ✅：3 条 query 全部 `mode=llm`，引用准确，耗时 0.76-1.12s，成本 ≈ ¥0.001/次
- 降级路径 4 项全过：超时(0.001s)回退、无 provider 回退、**空上下文不误判 no_citation**、
  JSON 容错（代码块 / 前后废话 / 缺字段）
- **抗幻觉行为已验证**：问「铝合金型材 6063-T5」但上下文只有 LED 产品 →
  模型答「依据现有记录无法确认」，has_answer=False —— 正是要的行为
- 回归：`demo_workflow.py` 三分支（正常 / 超时升级 / 打回重做）全通过；
