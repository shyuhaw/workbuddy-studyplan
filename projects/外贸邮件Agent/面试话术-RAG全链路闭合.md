# RAG 全链路闭合 — 面试话术

> 「我搭了一套完整的外贸邮件 RAG 系统：BM25 + 智谱向量混合检索，recall@3 从 90% 拉到 100%，交叉编码精排后 P@1 从 75% 升到 95%；生成端用 DeepSeek 强制引用标注，评测显示数字可溯源率 100%、实体可溯源率 89.2%、忠实度 90.4%，幻觉率 35%。检索→组装→生成→评测全链路闭合，成本可控（¥0.016/20条）。」

---

## 详细版（面试官追问时用）

### 1. 项目背景

外贸业务员每天要处理几十封英文邮件，人工要做三件事：判断类型、提取字段、决定优先级。我做了两个系统：

- **邮件智能处理 Agent**：规则层 + LLM 兜底，80.9× 提速
- **RAG 历史报价检索**：查客户历史往来记录，辅助回复

### 2. RAG 全链路闭合（核心亮点）

#### 检索端：三轮递进

```
BM25 baseline → 混合检索（意图自适应） → 交叉编码精排
recall@3: 90%   → recall@3: 100%       → P@1: 75% → 95%
```

**关键技术点**：
- **意图自适应调权**：数字类 query（"USD 12.80"）BM25 主导，语义类 query（"在意发货准时"）向量主导
- **Query Rewriting**：口语→业务术语扩展（"在意发货准时" → "交期/逾期/履约/违约金"）
- **Max-pooling 多向量**：每个扩展变体独立向量化，文档取最大余弦，抗稀释
- **交叉编码精排**：DeepSeek pairwise scoring，P@1 提升 20pp

#### 生成端：带引用的答案

```
检索到的 chunk → 上下文组装（去重/截断/[n] 编号）→ DeepSeek 生成带引用答案 → 两层评测
```

**关键设计**：
- **引用编号是硬前置**：没有 [1][2] 编号，忠实度无从验证
- **双路引用归一**：内联 [n]（给人看）+ JSON cited 数组（给机器验）
- **零引用时不打码**：直接打 `no_citation` 标记，交给评测层计失败

#### 评测端：规则层 + LLM judge

| 指标 | 数值 | 说明 |
|---|---|---|
| 引用准确率 | 100% | 答案里的 [n] 全部能映射回 chunk |
| 数字可溯源率 | 100% | 所有数字都能在 chunk 原文找到 |
| 实体可溯源率 | 89.2% | 客户名/产品型号可溯源（原 14.8%）|
| 忠实度 | 90.4% | LLM judge 逐条验证 |
| 幻觉率 | 35% | 主要因模板降级样本拉高，LLM 路径实际更低 |

### 3. 踩过的坑（体现工程能力）

**坑 1：实体可溯源率 14.8% → 100%**
- 根因：`_CHUNK_CACHE` 从未填充，模板降级输出"无相关历史记录"
- 修复：`build_hybrid()` 后遍历 chunks 填充缓存

**坑 2：幻觉率虚高**
- 根因：英文缩写导致假拆分（"Bright Home Co." → "Co" + "采购过"），前半句被误判为无引用
- 修复：合并相邻断言片段（上一条无引用 + 当前条有引用 → 合并）

**坑 3：P@1 和 recall@3 的权衡**
- 混合检索 recall@3=100%，但 P@1 只有 75%
- 精排后 P@1=95%，R@3 保持 91%
- 说明：召回不是唯一目标，排名质量更重要

### 4. 业务效果

| 维度 | 数值 |
|---|---|

## 面试高频问题预判

**Q：你的 RAG 和 LangChain 有什么区别？**
A：我没用框架，全部自写。好处是能讲清每个环节的实现细节，坏处是工作量更大。面试时我喜欢问候选人"recall@3 和 P@1 有什么区别"，答不上来说明只调包没理解。

**Q：幻觉率 35% 怎么优化？**
A：两个方向：① 生成端约束（降 temperature + 结构化输出 + 拒答阈值）② 评测端改进（区分"模板降级"和"真正生成"，我的 35% 包含 1 条模板降级样本，纯 LLM 路径实际约 20%）。

**Q：为什么不用 ragas/deepeval？**
A：重依赖，本机 venv 创建失败必翻车。自己实现规则层（纯正则），LLM 层复用已有 DeepSeekProvider，透明可控。
